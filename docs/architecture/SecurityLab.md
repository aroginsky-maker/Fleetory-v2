# PHASE 7 local security lab

The lab is an isolated, loopback-only integration environment. It is not a production deployment. It runs two independent step-ca instances (Agent and Admin), Keycloak, OpenBao in development mode, immudb and PostgreSQL. Keycloak currently serves as an OIDC/MFA integration target; Fleetory does not yet authenticate human users through it. immudb is an integration target; Fleetory does not yet export audit events to it.

From the repository root, run `./eng/start-security-lab.ps1`. The script creates random lab credentials in `../work/security-lab/lab.env`, starts the containers and writes the PostgreSQL connection string to OpenBao KV v2 at `secret/data/fleetory/fleetory-postgresql`. It also creates `../work/security-lab/openbao-token` for the Fleetory process. These files are outside Git and the script restricts their filesystem permissions to the current user. OpenBao development storage is ephemeral; rerun the script after its container restarts to reprovision the database secret.

Run `./eng/provision-security-lab-certificates.ps1` to issue separate Agent and Admin server/client certificates through their respective CAs. The script stores only leaf keys and public certificates outside Git in `../work/security-lab/certs`, restricts local access, and writes the server TLS bundles to OpenBao. The CA private keys remain in their separate CA volumes. Lab leaf certificates are short lived; rerun provisioning when they expire. The IDs in the client SANs are written beside the certificates and retained during certificate renewal.

Run `./eng/provision-security-lab-oidc.ps1` to configure the `fleetory` Keycloak realm, mandatory WebAuthn second factor, short access tokens, disabled password grant on the Fleetory browser client, fixed callback `http://127.0.0.1:4173/auth/callback`, S256 PKCE, API audience and WebAuthn AMR mappers. The script creates a lab user and keeps its random password in `../work/security-lab/certs/admin-user-password` with a private ACL. Keycloak assigns the user UUID; if the Admin certificate has another UUID, the script aligns `admin-person-id` and reissues the lab certificates. The realm must be accessed as `http://localhost:8088`, including by the browser, because WebAuthn RP IDs cannot be IP addresses. The callback is reserved for a future browser client; no callback application is started by this lab. The browser WebAuthn ceremony and successful signed-token request still need a live end-to-end check.

Build the Server, then run `./eng/verify-security-lab.ps1`. It starts Fleetory temporarily with `Fleetory:Secrets:Provider=OpenBao`, reads the token from the private file, checks `/health/ready` and stops the process. To check both real CA chains at startup, set `FLEETORY_Fleetory__AgentGateway__Enabled=true`, `FLEETORY_Fleetory__AdminGateway__Enabled=true` and distinct `Fleetory:Web:Port`, `Fleetory:AgentGateway:Port`, `Fleetory:AdminGateway:Port` values before running the verifier. To enable the Admin OIDC gate, set `FLEETORY_Fleetory__AdminGateway__Oidc__Enabled=true`, `FLEETORY_Fleetory__AdminGateway__Oidc__Authority=http://localhost:8088/realms/fleetory`, `FLEETORY_Fleetory__AdminGateway__Oidc__Audience=fleetory-admin-api` and `FLEETORY_Fleetory__AdminGateway__Oidc__ClientId=fleetory-admin-lab`. The script writes diagnostic logs to `../work/security-lab`. All published lab service ports bind to loopback.

The OpenBao provider requires an HTTPS origin outside Development. Development accepts plain HTTP only for a loopback origin. It reads bounded KV v2 `value` fields, caches them for the process lifetime, and fails startup if the database secret is missing or invalid. Server and Agent gateway TLS material may be stored under the existing `FleetorySecretNames` paths in OpenBao. The server certificate value can contain the leaf followed by up to three intermediate CA certificates. The pinned root is a separate secret. The Agent and Admin roots must remain distinct.

The lab checks service readiness, OpenBao-backed Fleetory startup with both real CA chains and OIDC configuration, and certificate-chain behavior in automated tests. A manual mTLS request with a step-ca issued Agent certificate reached the Agent gateway and returned 403 because the certificate has no Core binding, as expected. An automated mTLS test confirms that the Admin listener denies a valid certificate without an OIDC token with 401. The immudb PostgreSQL wire endpoint accepts `psql`, but a direct Npgsql 10 connection fails during backend type discovery. Audit export therefore needs its native client or a compatible gateway; simply wiring the current PostgreSQL sink to immudb would lose audit delivery. A local smoke test of the official immudb .NET gRPC SDK completed a verified write and read. The lab does not establish production CA policies, a completed browser WebAuthn ceremony, immutable audit retention, credential rotation, or secured command signing. These remain PHASE 7 work before the PR can merge.
