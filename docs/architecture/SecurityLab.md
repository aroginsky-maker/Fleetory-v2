# PHASE 7 local security lab

The certificate provisioning script requires PowerShell 7 or later to validate each leaf certificate against its private key.

The lab is an isolated, loopback-only integration environment. It is not a production deployment. It runs two independent step-ca instances (Agent and Admin), Keycloak, OpenBao in development mode, immudb and PostgreSQL. Keycloak supplies the Admin OIDC/MFA gate. immudb receives exported audit events when the optional export worker is enabled.

From the repository root, run `./eng/start-security-lab.ps1`. The script creates random lab credentials in `../work/security-lab/lab.env`, starts the containers and writes the PostgreSQL connection string and immudb audit password to OpenBao KV v2 under `secret/data/fleetory/`. It issues a separate, 24-hour, read-only token in `../work/security-lab/openbao-token` for Fleetory; the root token remains only in `lab.env` for provisioning. These files are outside Git and the script restricts their filesystem permissions to the current user. OpenBao development storage is ephemeral; rerun the script after its container restarts to reprovision the secrets and token.

Run `./eng/provision-security-lab-certificates.ps1` to issue separate Agent and Admin server/client certificates through their respective CAs. The script restricts `../work/security-lab/certs` before copying any leaf key, removes temporary leaf keys from the CA containers after each issuance, validates each new certificate/key pair and writes the server TLS bundles to OpenBao. The CA private keys remain in their separate CA volumes. Lab leaf certificates are short lived; rerun provisioning when they expire. The IDs in the client SANs are written beside the certificates and retained during certificate renewal. Before replacing an existing leaf pair, the script saves both prior files under the private `certs/history/` directory; an interrupted rotation can restore that pair. Archive access and cleanup remain the operator's responsibility. Production issuance and delivery need a separate controlled procedure.

Run `./eng/provision-security-lab-oidc.ps1` to configure the `fleetory` Keycloak realm, mandatory WebAuthn second factor, short access tokens, disabled password grant on the Fleetory browser client, fixed callback `http://127.0.0.1:4173/auth/callback`, S256 PKCE, API audience and WebAuthn AMR mappers. The script creates a lab user and keeps its random password in `../work/security-lab/certs/admin-user-password` with a private ACL. Keycloak assigns the user UUID; if the Admin certificate has another UUID, the script aligns `admin-person-id` and reissues the lab certificates. The realm must be accessed as `http://localhost:8088`, including by the browser, because WebAuthn RP IDs cannot be IP addresses.

Run `node ./eng/verify-security-lab-web-authn.js` with Playwright installed. Set `FLEETORY_PLAYWRIGHT_MODULE` to the local Playwright module path when it is not in Node's module search path, and optionally set `FLEETORY_CHROME_PATH` to an installed Chromium/Chrome executable. The verifier temporarily creates the callback listener, registers a virtual browser authenticator, performs S256 PKCE login, then logs in again with the passkey. The first registration token has no WebAuthn AMR; the second signed token must have `amr=webauthn`, the Admin certificate's subject UUID, client ID and API audience. With a real Fleetory Server and Admin client certificate, it verifies 401 without a token and 403 with the WebAuthn token when no RBAC grant exists. It removes the disposable lab user's passkey before and after the test. This resets that lab user's existing WebAuthn credential; use only the dedicated lab realm. The test normally supplies both the Admin root and intermediate CA to the client. Add `--require-server-chain` to verify delivery of the intermediate on the wire with a root-only client. On Windows, provision the root and intermediate in the appropriate OS certificate stores first, as described below.

Build the Server, then run `./eng/verify-security-lab.ps1`. It starts Fleetory temporarily with `Fleetory:Secrets:Provider=OpenBao`, reads the token from the private file, checks `/health/ready` and stops the process. To check both real CA chains at startup, set `FLEETORY_Fleetory__AgentGateway__Enabled=true`, `FLEETORY_Fleetory__AdminGateway__Enabled=true` and distinct `Fleetory:Web:Port`, `Fleetory:AgentGateway:Port`, `Fleetory:AdminGateway:Port` values before running the verifier. To enable the Admin OIDC gate, set `FLEETORY_Fleetory__AdminGateway__Oidc__Enabled=true`, `FLEETORY_Fleetory__AdminGateway__Oidc__Authority=http://localhost:8088/realms/fleetory`, `FLEETORY_Fleetory__AdminGateway__Oidc__Audience=fleetory-admin-api` and `FLEETORY_Fleetory__AdminGateway__Oidc__ClientId=fleetory-admin-lab`. The script writes diagnostic logs to `../work/security-lab`. All published lab service ports bind to loopback.

To run the audit export worker in the lab, set `FLEETORY_Fleetory__AuditExport__Enabled=true`, `FLEETORY_Fleetory__AuditExport__Sink=Immudb`, `FLEETORY_Fleetory__AuditExport__Address=http://127.0.0.1:8090/` and `FLEETORY_Fleetory__AuditExport__Username=immudb` before starting Fleetory. The password comes from OpenBao, and the worker drains committed PostgreSQL audit outbox entries. The lab uses the immudb administrator for convenience; production needs a separate least-privilege account, HTTPS and a retention/verification policy.

Run `./eng/verify-security-lab.ps1 -AuditPipeline` for a repeatable end-to-end check. It starts Fleetory with audit export enabled, inserts one lab audit event and outbox entry, waits for worker delivery, reads the EventId from immudb and verifies revision 1. It stops Fleetory afterward. This check uses only the local lab database and service ports.

Run `./eng/provision-security-lab-command-signing.ps1` after issuing the Agent lab certificate. It creates a non-exportable P-256 OpenBao Transit key and a one-hour sign-only token in `../work/security-lab-signer/command-signer-token`, outside the Server token directory. Its public SPKI key is written under `../work/security-lab/agent-trust/` with the DeviceId and key-version filename expected by `DirectoryCommandVerificationKeys`. Reprovisioning keeps the same public key and revokes the previous signer token where possible. A local smoke test used this limited token to sign `Inventory.Refresh`; the Agent verifier accepted it once and rejected the replay. The Server's read-only token could not call Transit sign. The lab runs under one desktop user and uses OpenBao development mode; production must isolate the signer on a separate identity/host, secure OpenBao storage and approve key rotation. No Server command signing or Agent execution endpoint is enabled.
Run `./eng/verify-security-lab-command-signing.ps1` for a repeatable end-to-end check. It reprovisions the one-hour signer token, signs a fresh `Inventory.Refresh` through Transit, verifies it with Agent trust and durable SQLite replay storage, then requires Transit to return 403 to the Server's KV-only token. After an OpenBao development-mode restart, the ephemeral Transit key ring may differ from Agent trust at **any** version, including a higher version left over from a previous lab run. The provisioner compares every trust file for this DeviceId with the current key ring and fails closed on a mismatch or missing version. Only for this disposable lab, run `./eng/verify-security-lab-command-signing.ps1 -ResetEphemeralTrust` to archive every stale target key under `../work/security-lab-signer/retired-trust/` before provisioning the current key. An isolated PowerShell test checks normal version overlap, reset refusal, complete retirement, DeviceId isolation and idempotence in CI. Never use that reset procedure for production trust rotation. The lab runs under one desktop user; production must isolate the signer on a separate identity/host, secure OpenBao storage and approve key rotation. No Server command signing or Agent execution endpoint is enabled.

The OpenBao provider requires an HTTPS origin outside Development. Development accepts plain HTTP only for a loopback origin. It reads bounded KV v2 `value` fields, caches them for the process lifetime, and fails startup if the database secret is missing or invalid. Server and Agent gateway TLS material may be stored under the existing `FleetorySecretNames` paths in OpenBao. The server certificate value can contain the leaf followed by up to three intermediate CA certificates. The pinned root is a separate secret. The Agent and Admin roots must remain distinct.

The lab checks service readiness, OpenBao-backed Fleetory startup with real CA chains, OIDC and the audit worker. A manual mTLS request with a step-ca issued Agent certificate reached the Agent gateway and returned 403 because the certificate has no Core binding, as expected. The browser verifier completed a real WebAuthn ceremony and signed-token request. The immudb PostgreSQL wire endpoint accepts `psql`, but a direct Npgsql 10 connection fails during backend type discovery. The audit sink therefore uses immudb's built-in REST API on port 8090. Live checks confirmed first delivery, matching retry, conflicting EventId rejection and a complete PostgreSQL outbox → Fleetory worker → immudb readback.

On 18 October 2026, a live lab renewal issued all four Agent/Admin leaf pairs. The new pairs passed certificate/private-key validation; the prior pairs were present in private history and matched a pre-rotation backup; client identity UUIDs were retained. The gateway root, server certificate chain and private key values in OpenBao matched the new local files. Fleetory started with both gateways enabled and the PostgreSQL outbox → immudb readback check passed. The isolated provisioner test also covers rollback when key copy fails and rejection of a mismatched certificate/key pair. The lab rotation is evidence for this script and environment, not for a production CA procedure.

Windows Schannel builds the outgoing server chain from its OS certificate stores. The original local probe, with only PEM secrets and no provisioned CA stores, sent only the leaf: root-only OpenSSL verification returned error 20 (`unable to get local issuer certificate`). The same published Fleetory Server and certificates sent the leaf and intermediate on Linux. The automated `Windows root-only TLS chain` CI job now provisions a disposable root into the runner's `LocalMachine\\Root` store and its intermediate into `LocalMachine\\CA`, starts the actual Fleetory Admin listener, and checks the wire with OpenSSL using only the root CA as client trust. It observed **two certificates and verify code 0**. The job removes both certificates afterward; it never changes the user's machine. Windows deployment must explicitly provision its approved gateway root and intermediate in the service host's corresponding certificate stores before starting Fleetory, and maintain them through CA renewal. The PEM server certificate secret alone does not populate those stores. Provisioning trust is a privileged host operation: validate the CA fingerprints and use the organization's certificate-management process. [Windows certificate stores](https://learn.microsoft.com/en-us/windows/win32/secauthn/certificate-stores) and [the .NET Windows certificate-context implementation](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Net.Security/src/System/Net/Security/SslStreamCertificateContext.Windows.cs) explain the platform chain source. The local lab does not establish production CA policies, immutable audit retention, credential rotation or isolated production command signing. These remain PHASE 7 work before the PR can merge.
