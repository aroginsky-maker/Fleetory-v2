# Independent retained public-probe cleanup

The independent parent now owns the actual retained controller's process fence
and the successful image-build, stopped-copy and sleep-worker create replies.
The fixed child publishes only public code, keeps its original 58 publication
descriptors, and uses the existing exact typed image/readback/runtime bindings.
The parent holds a separate 58-file public reference and verifies every context
and readback byte. Eighty-one fixed source inputs are pinned; preparation and the
separate fixed Python guardian pin 63 public inputs. The legacy forty-input
native publication and four extra runtime-input inventories keep their names.

This profile has its own fixed header with the Docker executable hash. The
original context-only header still admits exactly its original runtime roles
and does not start Docker. Private tool directories precede interpreter/system
directories. The only extended stages are a bounded image/readback frame plus
archive, a runtime-intent/preparation reply, a fixed runtime observation and its
typed binding reply. A fixed cancellation frame works at either binding stage.
The original context-only transport keeps its fixed 55-second whole-operation
window. The extended profile uses that same startup window until context
admission, then the minimum of the original retained/image expiry with a matching
fixed monotonic end. This does not renew either existing 60-second source window;
the exact end/origin is retained in its own immutable admission record. Source
pin checks recheck the clock before returning data.
Bounded writer/reader threads check the actual controller and fixed deadlines;
there is no generic command, path, endpoint, environment or secret channel.

The parent measures all three fixed cached bases itself, builds only the fixed
untagged public recipe, and obtains complete canonical immutable IDs directly
from its own bounded CLI calls. The child cannot supply an image/container ID
as parent cleanup authority. It receives the parent's checked image/readback,
creates the existing unobserved retained runtime and preparation, and keeps
preparation live until the complete parent create reply reaches the child.
Preparation closes immediately before the one consumed runtime observation;
the same original publication descriptors remain held through the handoff.
The child executes no Docker command and starts no service.

The fixed `run()` lifecycle prepares, watches and closes its own controller.
Leaving its context after a failed handoff attempts rollback of known own
resources before closing process/file capabilities. A consumed cleanup is never
replayed. Complete own creation replies remain usable for that rollback even
when the child dies before its final typed runtime binding.

Own replies have an in-process creator brand and are tied to that exact client,
fixed input hash, actual parent/controller identities, full ID, creation interval
and observation. Exclusive flushed start/build/resource/bound/delete/result
records retain failure/replay consumption. Returned dicts and serialized records
cannot recreate these live creator objects. All current record bytes retain
their exact canonical JSON plus one LF. No reset/restart adoption is provided.

The retained test worker uses the unchanged 660-second sleep command and fixed
384-MiB, one-CPU, 128-PID, UID/GID 3322 sandbox with read-only root, no network,
no capabilities, no-new-privileges, core-dump limit and two fixed noexec tmpfs
mounts. The parent starts a five-second ready cleanup lease after the typed handoff,
bounded by the original admission expiry. Its independent watcher observes its owned actual
controller or the lease, then freshly inspects the full immutable resource IDs
and compares every field with its own sealed profile before deleting. If an own-process image query fails during termination, a fixed three-second wait requires the actual owned exit signal; a still-live or changed identity refuses cleanup. The
stopped readback copy is never started and has its own stricter small profile.
The image removal uses the full ID and no parent pruning; cached bases must
remain unchanged and owned IDs must be absent from successful bounded listings.

Cleanup uses the parent's successful creator facts and fixed profile/creation
window. It does not reuse an old timestamp as a new observation or bypass the
original admission checks. The existing admission wrappers still require their
same wall/monotonic windows. Static profile parsers grant no authority. The
ready guardian can finish cleanup during its separate 75-second cleanup window
after the child/admission has expired; no child capability is revived. Controller closure always requires all owned process members absent. If the original source admission expired before closure, forced own-fence closure is recorded separately from graceful descriptor acknowledgement; the fixture does not demand an expired channel remain live.

Contract fixtures close retained capabilities before removing their checked temporary source directories on both operating systems. Only typed lineage/resource tests construct the full publication fixture; timer, framing and lifecycle assertions use their own small generated setup. The original 47 test methods and their assertions remain included. Four additional small contracts check the test-only paused observation comparison, including changed identity/profile, extra fields and wrong original state. Eleven removal contracts additionally require consumed failures, complete inner replies, actual absence, unchanged live creator objects and bounded cleanup without replay or forged closure. Nine of these tests share one generated source vector while each test gets a fresh owner, client, intent copy, record directory and handle stack. Records close before their temporary directory is removed; the source fixture closes after the class. The other two are pure reply checks. All 62 test methods and assertions remain unchanged, including the original 51; no admission, lease or cleanup clock is extended.

Portable contracts require positive typed bindings and refuse altered lineage,
foreign IDs/observations, arbitrary fields, malformed/partial replies, changed
persisted/held facts, expired admission, unsafe profiles, foreign creator objects
and replay. Linux CI reuses the existing public publication/reference fixture
for eleven actual controllers: lease expiry, controller death while the parent
waits, death after the own complete create reply before runtime binding, a real
original admission expiry, foreign observation, lost create reply,
partial create reply, CLI inspection failure, a paused own runtime, removal failure before Docker execution and loss of a complete successful removal reply. A standalone fixture supports
only those fixed cases for Windows Docker Desktop validation. No original input
or restored process is involved.

A lost/partial reply remains unknown to the guardian; no name lookup adopts its
resource and no positive cleanup result is returned. The negative test fixture
captures the complete inner reply at a separate creator call site, then disposes
its own test resources under fresh profile checks. This test-only disposal does
not reset or authorize the consumed guardian attempt. CLI/foreign-observation
failures likewise refuse deletion and retain consumption before fixture disposal.

The paused case uses only its own complete live creator reply and fixed full ID.
It pauses that worker, requires the observed profile to differ only in
`paused=true` (the runtime observation has no `status` field), and requires guardian refusal with zero removal
calls and no closed/success receipt. A separate own fixture sentinel must remain
unchanged. Only the live test creator unpauses its own exact observed object,
then rechecks the original complete profile before separate fixture disposal.
The consumed guardian start/delete is refused both before and after disposal;
the fixture never normalizes an observation presented to the guardian.

Two additional test interceptions affect only the guardian's exact own full-ID
runtime removal. A CLI failure before execution leaves the worker present and
the attempt consumed, with no closed/success receipt. Restoring transport permits
fresh checked fixture-only disposal; the guardian itself cannot retry.

For a lost removal reply, a separate in-process test creator fact holds the
original live resource, exact client/reply/record objects and unchanged cleanup
clock. Its trusted inner call captures the complete own removal reply and fresh
full-ID absence, then withholds the reply. The guardian refuses without closing
its runtime record or reporting success. Fixture disposal accepts that bounded
live fact for the already-absent worker and disposes other resources normally;
it never sets the guardian's closed flag or writes a substitute receipt. Absence
is checked again and no second worker removal is executed. Strings, serialized
records, changed creator objects, expiry, replay and a reappeared ID refuse.
If the removal witness was never attempted, ordinary fresh checked fixture disposal remains available; a failure before injection cannot strand a known own worker. These are injected CLI/response failures, not Docker daemon-death proofs.

Guardian/daemon/host death, other altered resources, pre-receipt crashes,
general bootstrap/compiler escaped sessions and independent rollback-resistant
custody remain open. The separate Python worker's thirty-second passive fallback
does not apply to this 660-second retained worker. There is no full RPO/RTO,
original service/config/provider/private-PKI recovery, issuer/token operation or
production deployment claim. Phase 7 and draft PR #2 stay open, including WORM,
independent people, post-restore human login, physical Agent and revocation.

The Windows CI job has a 20-minute overall limit after two runs exhausted 15 minutes. This runner limit covers the full validation workload; every test and the aggregate gate remain mandatory. Source admission remains 60 seconds, the ready cleanup lease 5 seconds, cleanup 75 seconds and the retained worker 660 seconds. Linux now has a 35-minute overall limit after CI373 exhausted 30 minutes during Sonar finalization, after all .NET tests passed and before analysis submission. The workflow contract refuses a silent return to 30 minutes or extension to 60. Provider/data job bounds remain unchanged.

The disposable pilot provisioning regression rejects PostgreSQL's socket-only temporary initialization server. A bounded fixture-only initialization gate keeps that listener available while the shared readiness function must refuse it; the gate is then released and final TCP readiness is required before provisioning. SQL diagnostics and generated passwords remain suppressed, and the fixture removes only its own container and volumes. This does not change original database restore or role/login evidence.

The next guardian split first establishes a policy-request boundary inside the
existing live creator. A public context contains only the original lease clocks,
nonce and source/receipt/ready-record digests. A request carries its context digest
and one fixed reason; IDs, commands, paths and replacement clocks are refused.
The creator retains its actual client, runtime reply/resource and ready-record
handle. It checks those same live objects and independently observes its held
controller fence and original cleanup clock before accepting a request. A refused
or accepted admission consumes the request attempt; public context bytes cannot
construct a new creator binding or authorize Docker. Cleanup success records the
validated request digest, while an interrupted pre-handoff rollback has no policy
request. The existing 62 contract methods and assertions remain; 28 generated
contracts exercise this new boundary. Native controller tests check the actual
request result separately from these generated models.
Mutation counterexamples establish a valid expiry or exit first, so an unrelated
early-lease refusal cannot hide a missing live-object or clock check.

The fixed policy now runs in a separate Python child, started only after the
creator retains its complete runtime reply and typed ready record. The existing
entry script accepts the sole fixed `--cleanup-policy` mode. The creator flushes
a consumed launch record before starting that child, holds its own OS process
fence and verifies its birth identity and pinned executable before releasing any
input. The header contains only both process identities, source/executable pins
and the public clock context. No resource object, resource ID, Docker argument,
credential or configurable command/path crosses this interface. The child checks
the same 81 pinned source files and its read-only creator/self process handles,
then emits a ready acknowledgement and at most one bounded cleanup request.
Its inherited environment uses the fixed host allowlist, without Docker-specific
runtime additions or credential variables. No Docker executable pin or action
endpoint is supplied. This is a fixed trusted-code interface; it is not
an OS sandbox against arbitrary code running as the same user.

The child uses the original wall and monotonic cleanup origins. Starting it does
not restart the 5-second lease or 75-second cleanup bound. A controller-exit event
on its one bounded input frame is only a policy hint: the creator independently
rechecks its held controller fence before admitting the resulting request. The
child cannot assert its own death over this protocol. Normal cancellation closes
only the separately owned process/fence; its absence is recorded before the
creator's cleanup dispatch. The result distinguishes creator, controller and
policy identities. The legacy `guardian` identity in the native case envelope
denotes the creator; `policyProcess` identifies the actual new child. The result
reports `creatorAliveDuringCleanup=true` and `guardianAliveDuringCleanup=false`
because the policy child has already exited before deletion.

EOF, nonzero exit, partial/trailing output, stderr and invalid requests do not
become positive policy admissions. After closing and checking the exact owned
peer fence, the live creator may use its separate `policy-peer-failed` path for
already-known own resources. That path requires the original live client,
reply/resource/record/context objects, an unexpired original cleanup clock and
no unknown create outcome. It is consumed independently of peer admission, never
retries a consumed Docker removal and records no validated request digest. It
cannot be constructed from a serialized report or a caller-selected process.

All 90 accepted contract methods/assertions remain included. Another 35 generated

failure. The modeled pipe writer uses only captured public context bytes; it
cannot read live creator records concurrently with the creator. These models
perform no OS fault injection or Docker operations. Native
normal lifecycle cases require a distinct policy birth identity, ready record,
successful own-fence closure and validated request. They are separate evidence

`guardianDeathCleanupVerified` remains false. Surviving-creator/daemon/host loss

81/63 source inventories and source, lease, cleanup and worker durations remain
unchanged. Three existing source files change and remain explicitly pinned;
no new source inventory entry is adopted.
