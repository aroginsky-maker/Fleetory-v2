# Retained publication guardian preparation

`RetainedGuardPreparation` is an in-process preparation object. It requires the
exact, still-unbound `RetainedRuntimeBinding` and its same live control session,
publication/image/readback capabilities and original publication descriptors.
A dict, serialized report, subclass, foreign session, already-bound worker or
failed observation cannot enter the preparation path. It cannot adopt a
container ID, start a guardian or execute Docker.

The attempt is exclusively created and flushed in the trusted operator's
retained directory before source, executable or hash admission. A second ready
record binds the frozen runtime intent to its persisted control record, image,
manifest, publication continuation/readback, held descriptors and runtime/code
hashes. Even coordinated changes to an object's in-memory intent/bytes/hash
cannot replace the original persisted intent. Unknown outcomes, flush errors,
expired admission or lost responses retain consumption; no reset is provided.

All 61 fixed public Python/profile inputs from the accepted public guardian
inventory are held and checked. The existing forty native-publication inputs
and four retained-runtime inputs remain held by the original capabilities;
their exact-type/schema guards and sixty-second windows are unchanged. The
current Python executable and a trusted caller-selected Docker executable are
held against their expected hashes. The preparing controller's real image and
birth are observed using a retained read-only self process object. No executable
is invoked. The Docker file in portable contracts is a generated canary, not a
daemon or an assertion that an actual Docker executable was used.

Every report rechecks process identity, all source/executable files, both
flushed records, live capabilities, both admission deadlines, unchanged intent
and an unused observation slot. Reports are fresh decoded copies. Later binding,
source mutation/closure, expiry, a foreign/forked caller or closed preparation
refuses reporting. Closing preparation releases only its own pins and records;
the source's descriptors and observation slot remain available to its enclosing
context. Persisted records and reports carry explicit false launch, cleanup,
guardian-start, own-create-receipt, original-input, PKI and full-recovery flags.

Twenty-two portable contracts cover those boundaries on Windows and Linux.
The existing Linux native retained-publication fixture also prepares this object
after actual image/stopped-copy readback, while the same 58 original publication
descriptors are still held. It checks real preparing-process identity and all
source pins, closes preparation, verifies that no observation was consumed, then
continues its existing controller-alive sleep-worker fixture. This is actual
preparation evidence, not independent retained-worker cleanup or authenticated
compiler/dependency/software origin. Local generated contracts and local
fixed-public-worker cleanup are reported separately from the Linux native test.

The concrete next integration keeps an actual retained controller and a separate
guardian process. The guardian must retain its own successful fixed public-worker
create reply, complete immutable ID/image/profile/labels and durable attempt
records. A checked anonymous process channel can bind the preparing controller's
actual birth/image to that creator; serialized preparation metadata is not an
authority token. Cleanup after controller death must rely on the guardian's own
creation evidence and fresh ID reobservation, not on accessing the now-dead
controller's capabilities or adopting its asserted container ID. Demonstrate
expiry, actual controller death, foreign/mismatched observations, lost create/
remove replies, CLI failure, restart refusal and known resource absence before
enabling the retained executor. The existing 660-second sleep profile has no
proven general guardian/daemon/host-death guarantee; the separate public Python
worker's thirty-second passive fallback must not be attributed to this profile.

No secret, original backup, private PKI, provider, issuer, production token or
VPS access is added. Original-service recovery, full RPO/RTO, human/physical-Agent
acceptance, independent WORM/custody and production approvals remain open.
Phase 7 remains open and PR #2 remains draft/unmerged.

The next [owned controller context transport](RetainedContextTransport.md) keeps
the actual retained controller in a child process and validates public bytes
against the independent parent reference. It performs no Docker dispatch.
